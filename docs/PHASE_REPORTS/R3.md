# تقرير المرحلة R3 — محرك التحليل الأمني الموحد

**التاريخ:** 2026-11-13
**التفويض:** R3 معتمدة ومنفذة؛ R4 وما بعدها غير مصرح بها.
**الحالة:** مكتملة من ناحية التنفيذ والاختبار؛ بانتظار مراجعة مدير المشروع.

## تدقيق ما قبل التنفيذ

بدأ العمل على `/home/ubuntu/chainscope-x`، فرع `main`، عند R2 final commit `9872cb8` (`Add R2 manager handoff`) وشجرة عمل نظيفة. جرى التحقق من حالة المشروع وعقود R1، وسجل الأدوات ومسجل الآثار ومخزن الأدلة وعدّاء المختبر واختبارات R0–R2. حُفظ تاريخ R0/R1/R2 وحزمها. لم يُنشأ مشروع جديد ولم تُستخدم خدمات خارجية.

البيئة: Linux ARM64 (`aarch64`)، Python 3.12.3، Git 2.43.0، Pydantic 2.14.2، FastAPI 0.162.0. لم تثبت حزم جديدة.

## المنفذ

- `AnalysisService` ينفذ خط تحليل واحد لتقرير R2 واحد فقط: تدقيق provenance، مقارنة الآثار، بناء الرسم، تقييم السياسة، وتوليد findings.
- `EffectMismatchAnalyzer` يقارن manifests والقدرات/الأذونات وقوائم الموارد والوجهات مع الأحداث والاستدعاءات والتغطية. يغفل الآثار الاختيارية. غياب المطلوب تحت نجاح وتغطية كاملة للواجهة فقط يصبح فرقًا؛ غير ذلك يظل غير حاسم.
- `CapabilityGraphBuilder` يستخدم resource IDs وخط نسب R2 وevent IDs الفعلية. لا يقبل lineage التحويل إلا إذا طابق قراءات `READS` الناجحة للاستدعاء نفسه. الحواف مرتبطة بالتنفيذ والاستدعاء والأدلة والتصنيف. يقيد المسارات بحد عمق 16 و512 مسارًا، ويمنع دورات العقدة ويستبعد التنفيذ الآخر.
- `PolicyEvaluator` يدعم قواعد الوصول إلى الأصول والكتابة والوجهات الحساسة/الممنوعة والموافقة. يتحقق أولًا من حالة القاعدة وتاريخها ونطاقها وبنيتها ومتطلبات evidence. لا تُقبل الموافقة إلا إذا ربطت `approved_event_ids` بالحدث المستهدف في invocation نفسه. لا تعتبر الوجهة الخارجية مخالفة بذاتها.
- `FindingGenerator` يعطي تصنيفًا قابلًا للتفسير، ولا يؤكد DENY إلا بحدث الشرط داخل path موجود في الرسم ومراجع evidence المحلولة والمتحقق منها لذلك path. لا يساوي فرق الإقرار بمخالفة سياسة.
- أضيفت عقود R3 بقيم اختيارية افتراضية، منها `GraphEdge.invocation_ids` ومراجع finding؛ أضيفت `EffectType.USES` لتمثيل علاقة الرسم المطلوبة مع بقاء القيم السابقة وأنواع الأحداث الفعلية في R2 كما هي. لا dependency أو LLM أو DB أو API أو خدمة شبكة.

## نتائج السيناريوهات A–H

| السيناريو | النتيجة الفعلية |
|---|---|
| A — تدفق داخلي آمن | نجح؛ سجل أحداث فعلي ورسم داخلي يحافظ على تحويل/إنشاء/كتابة؛ لا مسار إرسال محظور ولا فرق manifest. |
| B — الأثر المعادي الإضافي | رُصد `TRANSMITS` غير المعلن، والعملية/الوجهة خارج تصريح Workspace Storage. النسخ تم إلى sink محاكاة محلي فقط. النتيجة `POTENTIAL_RISK` لا مخالفة مؤكدة لغياب سياسة حاسمة. |
| C — مسار سري متعدد الأدوات | `CONFIDENTIAL` من أصل إلى تحويل وتخزين ومشاركة خارجية؛ قاعدة نشطة مطبقة رفضت المسار. `CONFIRMED_VIOLATION`، شدة `CRITICAL`، مع مسار وأحداث واستدعاءات ومراجع evidence صالحة. |
| D — تغطية PARTIAL/UNKNOWN بلا إرسال إيجابي | في الحالتين كانت النتيجة `INCONCLUSIVE`، ولم يظهر ادعاء السلامة. |
| E — حدث ممنوع إيجابي مع نقص آخر | حدث الإرسال الموثق أكد المخالفة رغم `PARTIAL` غير مرتبط بالمسار؛ قيد التغطية بقي ظاهرًا في النتيجة. |
| F — وجهة خارجية مسموحة صراحة | البيانات `PUBLIC` والوجهة مصرح بها بقاعدة صالحة؛ لا مخالفة ولا خطر مبني على كون الوجهة خارجية. |
| G — سياسة غير منطبقة | سُجلت حالتا `INACTIVE` و`OUT_OF_SCOPE`؛ لم تنشأ مخالفة على أساسهما. ظل الإرسال الحساس غير المحسوم خطر مراجعة محتملًا فقط. |
| H — نسب تحويل مفقود | سُجل `INCOMPLETE_COMPARISON` و`transformation_lineage_missing`؛ لم يتصل أصل الإدخال بمخرج التحويل في المسار. النتيجة `INCONCLUSIVE`. |

واختبرت إضافيًا قيود الوصول إلى أصل وكتابة مورد محظور وحظر وجهة صريحًا ومطلب موافقة لا تملك R2 واجهة رصد له؛ الأخير بقي خطرًا محتملًا لا مخالفة مؤكدة.

## التحقق

- اختبارات R3 المركزة: **25/25 ناجحة**.
- مجموعة R0–R3 الكاملة: `python3 -m unittest discover -s tests -v` — **64 ناجحة، 0 فشل** (3 R0 + 12 R1 + 24 R2 + 25 R3).
- `python3 -m compileall -q app tests` — ناجح.
- تصدير والتحقق من **13** ملف JSON Schema — جميعها JSON صالح.
- `git diff --check` — ناجح بعد آخر تعديل وثائقي.
- اختبارات الرصد تحظر socket أثناء السيناريو المحلي؛ لا يجري الإرسال عبر شبكة. تغطي الاختبارات أيضًا كل عمليات الأدوات الست، invocation ID المكرر، denylist فارغة، requirement للتغطية/الموافقة، وربط event/evidence المصطنع غير الصالح.

## الحدود والقرارات المطلوبة

التغطية كاملة فقط ضمن محولات R2 الاصطناعية المحددة، وكل بيانات المختبر/evidence عابرة للعملية. لا يثبت التحليل غياب المخالفة خارج ذلك النطاق. لا يمكن إثبات غياب الموافقة دون أداة رصد موافقات صريحة. لا تزال ملاءمة الجهاز اللوحي والمتطلب الأكاديمي SQL/NoSQL غير محسومين من مراحل سابقة.

المطلوب من المدير: مراجعة/قبول R3 فقط. أي تصميم واجهة موافقات أو توسعة أخرى وأي مرحلة R4 تحتاج قرار تفويض جديد. لا يبدأ R4 تلقائيًا. معرف Git النهائي وسلامة الشجرة يسجلان في ملف التسليم بعد حفظ commit.
